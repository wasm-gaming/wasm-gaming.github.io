# Homogenize engine integration across the ecosystem

2026-11-12 · cross-repo plan, written from `wasm-gaming.github.io`

Goal: every engine repo integrates the same way — same contract version, same SDK shape,
same package layout, same Makefile vocabulary, same CI — using the two engines already on
contract 0.3.2 as the reference. **Nothing is implemented until this plan is approved.**

### Drift found

1. **Two contracts in the wild.** 10 of 12 engines still export `{ manifest, load }` (pre-1.0).
   Only rsdkv4 and ppsspp extend `EngineSDKBase`. A host cannot drive both kinds with one code path,
   which is the whole point of the contract.
2. **Unbounded ranges.** `*` and `>=0.2.0` will happily resolve 0.3.x, whose API is incompatible
   with the old `load()` SDKs. These builds are one `npm install` from breaking.
3. **Two reference engines disagree with each other**:
   - dependency kind: rsdkv4 = `peerDependencies` + `devDependencies`; ppsspp = `dependencies`;
   - layout: rsdkv4 = `src/<id>.sdk.ts` + `src/<id>.options.ts`, `dist/<id>/`; ppsspp = `src/<repo>.ts` + split modules, `dist/` flat;
   - Makefile: rsdkv4 = `build / build-sdk / build-wasm / demo / test / typecheck / preview / up / release-check`;
     ppsspp = `build / wasm / site / docs / test / smoke / publish`;
   - tests: ppsspp has conformance + lifecycle tests; rsdkv4 only type-checks.
4. **Workflow names**: `build.yml` vs `build-main.yml` for the same job.
5. **Stale docs in the pilot itself**: `rsdkv4-wasm/README.md` "Contract surface" still documents
   `import { manifest, load }` although the SDK is class-based since 0.2.x.
6. **This site** advertises the old API in every snippet (`js/projects-data.js` `CODE_EXAMPLES`),
   shows outdated versions (engine-specs v0.2.5, rsdkv4 v0.1.3), omits ppsspp-wasm and says
   "13 repositories / 6 emulators".

## Target: one canonical engine repo

Base: **rsdkv4-wasm** (it is the pilot and the old engines' Makefiles are already closest to its
vocabulary), taking from **ppsspp-wasm** what rsdkv4 lacks (real tests).

| aspect | canonical |
| --- | --- |
| contract | `@wasm-gaming/engine-specs` `^0.3.2` as **peerDependency + devDependency** |
| SDK | `class <Id>SDK extends EngineSDKBase` + `class <Id>Play extends EnginePlayBase`, `static id`, `static version` |
| spec | `<ID>_SPEC` (config / options / assets / storage, `default` only in the spec) in `src/<id>.options.ts` |
| conformance line | `export const <ID>_ENGINE: EngineSDKConstructor<<Id>Payloads> = <Id>SDK;` + `export default <Id>SDK` |
| files | `src/<id>.sdk.ts`, `src/<id>.options.ts`; output `dist/<id>/<id>.sdk.{js,d.ts}`, `dist/<id>/<id>.{js,wasm}`, `dist/engine-specs.js` |
| package.json | `exports` `.` (+ `./options`), no `scripts` (Makefile owns the build), `engineContract` field |
| Makefile | `install build build-sdk build-lib build-specs build-wasm demo build-typedoc test typecheck preview up release-check clean help` |
| tests | `tests/conformance.ts` (type-level) + `tests/lifecycle.test.mjs` with a fake module (from ppsspp) |
| CI | `.github/workflows/build.yml` (workflow_call, `version` input, `sync-version.mjs`) + `release.yml` |
| docs | README "Contract surface" with the chained API; typedoc site as Pages home |
| agent docs | same `CLAUDE.md` / `AGENTS.md` / `SESSIONS/` convention (already shared) |

Removed per engine: `src/<id>.manifest.ts`, `build-manifest`, `load()`, `onEvent`, `storageNamespace`
(→ `storage({ namespace })`), `build-main.yml`.

## Phases

### Phase 0 — Fix the references (small, unblocks everything)
- rsdkv4-wasm: rewrite README "Contract surface" to the class API.
- ppsspp-wasm: move engine-specs to peer + dev; align Makefile target names and file names to the table.
- engine-specs: add `docs/ENGINE-TEMPLATE.md` (or a `template/` dir) with the canonical skeleton,
  Makefile, workflows and conformance test, so each migration is a copy-and-fill.

### Phase 1 — Pin the old engines (zero-risk, one commit each)
Replace `*` / `>=0.2.x` with the exact last 0.2.x they build against (`~0.2.7`), so nothing breaks
while migration is pending. Rename `build-main.yml` → `build.yml`.

### Phase 2 — Migrate to the 1.0 class, simplest first
Order by SDK size and similarity: blastem → fbneo → rsdkv3 → rsdkv5 (siblings of rsdkv4) →
jgenesis → smbros → snes9x → mGBA → geolith → celeste. Each one:
1. session file in that repo; 2. split options into `config` (engine) / `options` (session);
3. port `load()` body into `open()` / `close()` / `mounted()`; 4. conformance line + lifecycle test;
5. update its demo host; 6. bump minor version and release.

### Phase 3 — This site
- Snippets: chained API (`new Snes9xSDK().assets({ rom }).mount(el).start()`).
- Catalog data: real versions, contract badge per engine (1.0 / legacy), add ppsspp-wasm, fix stats.
- Ideally generate `projects-data.js` from each repo's `package.json` at build time so it cannot drift again.

## Extension · 2026-11-12 — Constraint: every repository must work on its own

Owner's decision: **each repository must work independently.** Homogeneity comes from shared
*conventions* (same layout, names, targets, CI), not from repos consuming each other at build or
run time.

### Coupling that exists today and breaks that rule

| coupling | where | effect |
| --- | --- | --- |
| **Shared demo shell** copied out of `node_modules/@wasm-gaming/engine-specs/demo` | rsdkv4 (`SPECS_DEMO`), snes9x, geolith, celeste (`DEMO_SRC` / `SPECS_DEMO`), others | an engine's demo changes, or breaks, when engine-specs publishes; rsdkv4 already overrides two of its components to fix bugs in it |
| **Sibling checkout** `link-specs` (`SPECS_SRC`) | mGBA-wasm | build depends on a second repo cloned next to it |
| **Bare `@wasm-gaming/engine-specs` specifier** in the built SDK | rsdkv4, ppsspp | a host must supply an import map or a bundler, or the published package does not load |
| `peerDependencies` on the contract | rsdkv4 | host is responsible for installing the contract |

### Revised target

1. **Contract = one versioned npm dependency, nothing more.** `@wasm-gaming/engine-specs` goes in
   `dependencies` with a caret range (`^0.3.2`), never `*`, never a sibling path. *(Resolves open
   decision 1: regular dependency, not peer.)*
2. **The published SDK is self-contained.** `make build-sdk` emits `dist/<id>/<id>.sdk.js` with the
   contract's runtime bundled in (or its import rewritten to the shipped `dist/engine-specs.js`), so
   `import Sdk from '…/<id>.sdk.js'` works from a plain static server with no import map.
3. **Each repo owns its demo.** The demo/host lives in `src/demo/` of that repo; no
   `cp -R node_modules/@wasm-gaming/engine-specs/demo`. Removed targets: `link-specs`, the
   `SPECS_DEMO`/`DEMO_SRC` copies. `engine-specs/demo/` stays as the contract's *own* demo only.
4. **Template is copied, never consumed.** The canonical skeleton (Makefile, workflows, tests,
   `CLAUDE.md`/`AGENTS.md`) lives in `engine-specs/template/` as a reference to copy once; after
   that the engine repo has no link to it.
5. **Acceptance test per repo:** on a clean machine, `git clone` → `npm ci` → `make build-sdk test demo`
   → `make preview` works, with no other wasm-gaming repo present. Added to each repo's CI as is.
6. **This site** keeps its catalog as static data in this repo (no build-time fetch of other repos);
   versions are updated by hand, or by a script run on demand that only writes `projects-data.js`.

### Phase changes
- Phase 0 adds: remove the shared demo shell / `link-specs` from rsdkv4 and mGBA first; make the
  rsdkv4 SDK bundle self-contained; move rsdkv4 to `dependencies`.
- Phase 2, per engine, adds step 0: inline its demo into `src/demo/` before touching the SDK.

## Extension · 2026-11-12 — Consumer, exceptions, WASMFS, priority

- **Consumer**: the target host is the Netflix-style launcher
  [jgermade/play.germade](https://github.com/jgermade/play.germade); its plan is
  `SESSIONS/2026-11-12_00h00.launcher-consumes-engine-packages.session.md` there.
- **Exception to independence**: `@wasm-gaming/engine-specs` is a dependency of every engine
  (and of the launcher). Everything else stays standalone.
- **WASMFS namespace per engine**: storage lives under `<engine-id>/<namespace>/` (OPFS root =
  WASMFS `/data`), the prefix enforced by the engine via a shared `storagePath()` helper in
  engine-specs. Today rsdkv4, snes9x, mGBA and geolith all default to a shared `default/`.
- **Priority = engines that already work in the launcher**, replacing Phase 2's order:
  rsdkv4 → rsdkv3 → rsdkv5 → fbneo → blastem → jgenesis → celeste; then ppsspp, snes9x, mGBA,
  geolith, smbros.
