# A settings screen in every engine app — proposal — 2026-11-16

Status: **proposal, awaiting approval.**

## Request

The owner (2026-11-16): the emulators lack a settings screen, and so do the RSDK engines where they
have graphics settings such as the type of smoothing. Each engine should show the settings it
supports.

## What exists today (surveyed in each repo)

| Engine | Settings it already has | Where | Shown in its app today |
| --- | --- | --- | --- |
| blastem | `renderFilter` pixelated / smooth (CSS, **live**) | contract `config` | no |
| fbneo | `renderFilter` pixelated / smooth (CSS, **live**) | contract `config` | no |
| snes9x | 11 in a catalog (groups Video / Audio / Emulation, with labels and value labels): image filtering, aspect 4:3 / 1:1, crop overscan, volume, DSP interpolation, region, sprites per line, Super FX clock, multitap… `live` unless `requiresReset` | catalog → contract `options` | no (its old ESC menu is turned off by the app: `escMenu: false`) |
| mGBA | 11 in a catalog: image filtering, aspect, interframe blending, volume, system, GB model, BIOS… | catalog → contract `options` | no (same) |
| jgenesis | 26 in a catalog, all live through `WebConfigRef`: nearest / linear filtering, blending shader (NTSC composite, xBRZ 4x, horizontal blur), prescaling, aspect ratio per system, region, sprite limits, low-pass filter… | `jgenesis.options.ts` | no (its ESC overlay is turned off by the app) |
| rsdkv5 | none graphical (`vsync`, `language`, `region`, read once from `Settings.ini`). The web build uses RSDK's SDL2 render device: no shaders. The canvas is the native 424×240, scaled by CSS `image-rendering: pixelated`. | contract `config` | no |
| rsdkv4 | none graphical. The canvas is CSS-scaled with no `image-rendering` set, so the browser smooths it today (to check). | contract `config` | no |
| rsdkv3 | none graphical. `WindowScale=2`, CSS `pixelated`. | contract `config` | no |
| sonic3air | none in the contract. **The game's own Options menu** already has the display settings (upscaling: pixel-perfect / soft / xBRZ / hqx, filtering, scanlines). The canvas is drawn at the window's width, so a CSS filter would do nothing. | the game | yes, in the game itself |

So most of the settings already exist and work live. What is missing is (1) a way for the contract to
say which properties are **player-facing**, with a name a player reads and names for their values,
and (2) the screen itself in each app.

## Proposal

### 1. engine-specs (minor: 0.6.0) — the contract and the shared screen

- `PropertyDefinition` gets three optional, backwards-compatible fields:
  - `label` — the name shown to the player. **A property with a `label` is a setting**; one without
    stays internal (URLs, debug flags…).
  - `group` — `'video' | 'audio' | 'emulation' | 'game'`, the screen's sections, in that order.
  - `valueLabels` — the names of the `enum` values, in the same order (`['Píxeles nítidos', 'Suavizado']`).
- `live` keeps its meaning. A non-live setting is shown with the note "se aplica al reiniciar"
  ("applies on restart"). It is saved and handed to the SDK on the next start. Nothing restarts
  silently.
- A **pure model** and a small runtime, so nine apps don't each re-derive it:
  - `settingsModel(described)`: from `config()` / `options()` descriptors to groups → rows (label,
    current value and its label, next and previous value, live, description). Booleans are "Sí" /
    "No"; enums cycle; numeric enums (e.g. volume) step.
  - `loadSettings(engineId)` / `saveSettings(engineId, values)`: OPFS `settings/<engineId>.json`,
    where the app keeps the player's choices.
- **UX.md, a "Settings" section:**
  - The pause menu gets **Ajustes** after the engine's own entries, before "Volver al lanzador".
  - A row shows its label and its value.
  - `left` / `right` change the value (enums cycle, booleans toggle), and so does `accept`.
  - `more` shows the description. `back` closes.
  - A change applies at once when the setting is live, and is saved either way.
  - The game stays paused behind the screen, and the picture updates under it for video settings,
    so the player sees the effect.
  - A "Restablecer" (reset to defaults) row at the end, with a confirm.
  - On touch, tapping a row cycles it.
- The demo gets a settings page against the demo engine, and there are tests for the model.

### 2. Each engine (its own record, PR and release, after engine-specs 0.6.0)

| Engine | Screen | Work |
| --- | --- | --- |
| blastem, fbneo | **Vídeo**: Suavizado (Píxeles nítidos / Suavizado) | labels on `renderFilter`; "Ajustes" in the app |
| snes9x, mGBA | everything in their catalogs, grouped Vídeo / Audio / Emulación; reset-only ones marked | catalog labels → `label` / `group` / `valueLabels`; "Ajustes" in the app |
| jgenesis | the 26 settings: Vídeo (filtering, shader, prescaling, aspect ratio), Audio, Emulación (region, sprite limits…), the per-system ones only when that system is running | the same mapping, for options the running core supports (`engineConfig.supports`) |
| rsdkv3 / v4 / v5 | **Vídeo**: Suavizado (CSS `image-rendering`, live). The native shaders are not in these web builds (v5 uses SDL2's renderer). rsdkv4 becomes pixelated by default, like v3 and v5. | `config.renderFilter` + "Ajustes" in the apps; check rsdkv4's canvas size first |
| sonic3air | no "Ajustes" entry: the game's own Options menu has its display settings, and they apply live | — (documented in its README) |

### 3. play.germade

Bump every engine to its release with "Ajustes". Nothing else: the screens live in the engine apps,
and the saved settings sit in the same OPFS origin.

## Open decisions for the owner

1. **Scope of a setting: per engine (all its games), or per game?** Proposal: per engine
   (`settings/<engine>.json`). Smoothing or volume is a preference, not a property of one game.
2. **Language of the labels.** The apps are in Spanish and the catalogs in English ("Image
   filtering"). Proposal: `label` / `valueLabels` in Spanish, the UI language of every app; the
   `description` (for developers) stays in English.
3. **How much of each catalog.** Proposal: everything the engine supports, as asked ("show the
   settings each engine allows"), grouped. Hacks such as Super FX overclock or the sprite limit go
   under Emulación with their description.
4. **Integer scaling** ("Escalado: ajustar / píxeles enteros"), next to smoothing in Vídeo, for the
   engines that size their own canvas: optional, in the same pass or later.
5. **Order with the pending `/roms/` task** (rom-manager in play.germade, plus the 768 / 460 / vw
   styles). Proposal: `/roms/` first, as agreed, then this.

## 2026-11-16 02:10 — The owner's answers, and what they change

Adds: the decisions, the language requirement (wider than this screen), and the question about an
extra smoothing from the launcher.

### Decisions

1. **Scope: per engine.** One file per engine, OPFS `settings/<engineId>.json`, shared by all its
   games.
2. **Language — a new rule for the whole ecosystem:** "All the UI of the application and the engines
   must be in English and Spanish, falling back to English. All the code, always in English
   (variables, comments, etc.)." This reaches beyond the settings screen:
   - **engine-specs**:
     - `type Locale = 'en' | 'es'`.
     - `type Localized = string | { en: string; es?: string }`; a plain string is English.
     - `localize(text, locale)` falls back to `en`.
     - `resolveLocale(preferred?)`: the host's locale, else the first of `navigator.languages` that
       is supported, else `en`.
     - `EngineAppHost` gets an optional `locale` (the launcher passes its own).
     - The settings fields become `label?: Localized` and `valueLabels?: Localized[]`.
   - **Every engine app** (rsdkv3, rsdkv4, rsdkv5, blastem, fbneo, snes9x, mGBA, jgenesis,
     sonic3air) moves its strings ("Continuar", "Pausa", "Volver al lanzador", errors, hints…) into
     an `{ en, es }` table read through the host's locale. Today they are Spanish only; sonic3air's
     brand-new app included.
   - **SDK error messages** stay as they are (English, for developers). The apps show their own
     localized text and keep the SDK's reason as a detail.
   - **play.germade**: its UI is Spanish only today. It gets the same `{ en, es }` treatment, follows
     the browser by default, has a language choice in the launcher, and passes `locale` to the apps.
     That is play.germade's own record (a separate change).
   - Code: identifiers and comments are already English everywhere. Only UI strings change.
3. **Breadth: everything each engine supports**, grouped Vídeo / Audio / Emulación ("Video /
   Audio / Emulation" in English), with descriptions; settings that need a restart are marked.

### "An additional smoothing from play.germade?" (the owner's question on point 4)

Possible, as a **shared screen filter**, but it belongs in engine-specs + the engine apps rather
than in the launcher: the app owns the canvas and the settings screen, and the launcher only mounts
the app.

- `createScreenFilter(canvas, { filter })` in engine-specs. A WebGL2 canvas laid over the engine's
  canvas samples it every frame and draws it through a shader; the engine's own canvas is hidden.
  Candidate filters:
  - **Nítido** (nearest), **Suave** (bilinear);
  - **Bilineal nítido** (integer prescale then bilinear: crisp without shimmer, usually the best for
    pixel art);
  - **Scanlines / CRT**;
  - later maybe xBRZ / ScaleFX.
- Where it helps: engines that draw at their native resolution and are CSS-scaled (rsdkv3/v4/v5,
  blastem, fbneo, snes9x, mGBA). Not sonic3air (drawn at window resolution, with its own upscalers in
  its Options) or jgenesis (WebGPU, with its own shaders, which the settings screen will show).
- It shows up in Ajustes → Vídeo as one more setting ("Filtro de pantalla" / "Screen filter").
- Risk to check per engine: reading a WebGL canvas without `preserveDrawingBuffer` only works in
  the same frame, after the engine draws. 2D canvases (snes9x, mGBA) have no such issue.
- Proposed as a **second phase**, after the settings screen and i18n, starting with "Bilineal
  nítido" and scanlines.

### Order (proposed)

1. `/roms/` in play.germade (agreed earlier, with the 768 / 460 / vw styles; in English and Spanish
   under the new rule).
2. engine-specs 0.6.0: i18n helpers, settings fields, settings model, `loadSettings` /
   `saveSettings`, UX.md.
3. Each engine: an i18n app plus "Ajustes", one PR and release each.
4. play.germade: i18n + language choice + engine bumps.
5. Screen filter (phase 2).

## 2026-11-16 21:10 — Added by the owner: key remapping and a fullscreen hotkey

Adds: two more things for the same pass over the engines. The owner (2026-11-16): "cuando toques los
motores, añade la opción de remapear teclas y un hotkey para teclado y gamepad que haga toggle
fullscreen".

- **Key remapping**: in Ajustes, a "Controles" / "Controls" group.
  - The engine's buttons (from its input description) each show their key and their gamepad button.
  - Choosing a row waits for the next key or button press, which becomes the new binding. Escape
    cancels.
  - "Restablecer" restores the defaults.
  - Saved per engine with the other settings.
  - Applied through the engine's own input mapping where it has one, else through engine-specs'
    input layer.
- **Fullscreen toggle**:
  - Keyboard: **F11 is the browser's own and cannot be relied on**. Proposed default: **F**
    (outside text fields), remappable like the rest.
  - Gamepad: proposed **Select + Y** (Select + Start already opens the pause menu).
  - It toggles `requestFullscreen()` on the app's root. It is also an entry in the pause menu,
    since browsers only allow fullscreen from a user gesture: a pad press counts in Chromium but
    not everywhere.
- **Where**:
  - engine-specs 0.6.0: a shared `createFullscreenToggle(root, input)`, the remap model, and the
    capture helper.
  - Each engine app: its button list and any engine-specific mapping.
- **Detail to settle when engine-specs 0.6.0 is drafted**: the exact defaults (F, Select + Y) and
  how each engine exposes its bindings (the RSDK engines read their own `Settings.ini` keys;
  snes9x / mGBA / jgenesis / blastem / fbneo map in the SDK). Each engine's record lists what it
  supports.

## 2026-11-16 21:20 — The fullscreen key, set by the owner

Adds: the owner's choice for the keyboard: **Cmd+Enter on macOS, Alt+Enter on Windows / Linux**.
This replaces the proposed F.
- It is the classic emulator shortcut. It is also free in the browsers: Alt+Enter is not taken in
  Chrome or Firefox on Windows / Linux, and neither is Cmd+Enter on macOS.
- The platform is read from `navigator.userAgentData?.platform`, else `navigator.platform`.
- Ignored while a text field has focus.
- Remappable like the other bindings.
- The gamepad default (Select + Y) is still a proposal.
